## Pattern 1 — Two-Claude Architecture

**The pattern.** Two Claude surfaces with distinct roles:
- **Chat-Claude** (Claude.ai web/desktop/mobile): strategy, planning, writing, customer-facing artifacts, adversarial review, working through ambiguity.
- **Code-Claude** (Claude Code in terminal): code, tests, file edits, running builds, executing migrations, committing to git.

They do **not** talk to each other directly. They both talk to Linear; Code-Claude also talks to GitHub. Linear is the bridge.

**Why it works.**
- Each Claude has tool access that fits its role. Chat-Claude can't run code; Code-Claude shouldn't be doing 30-message strategic conversations.
- Founder mental model is clean: "this is a thinking problem, open chat" vs "this is a build problem, open terminal".
- No copy-paste between systems — both write to Linear.

**Keep / change.**
- KEEP entirely. This is the spine.
- Generalize Linear-specific language. Linear is **the recommended bridge**; the stack should explicitly list alternatives (Notion, Obsidian + git, GitHub Projects) and what the founder loses by switching.

## Pattern 2 — Linear as Live Context Store

**The pattern.** Linear hosts seven projects in a single team:
1. **Strategy** — long-form documents + append-only ADRs (numbered, `type:long-lived`, status `Done`)
2. **Product** (or **Spec**) — long-form product/technical specifications
3. **GTM** (or **External**) — outreach templates, customer-facing artifacts (optional, depends on project type)
4. **Customers** (or **Prospects** or **Stakeholders**) — one issue per external party, comments = conversation log (optional)
5. **Outreach Log** — append-only one issue per message sent (optional, GTM-heavy projects only)
6. **Sync Queue** — pending Linear→GitHub commits, label `sync:pending` → `sync:synced` → `sync:conflict`
7. **Build Log** — one issue per ISO week, body has fixed sections

Issue prefix: project-specific 3-letter prefix.
Labels: `vertical:*`, `country:*` (project-specific), `sync:*` (universal), `type:long-lived` (universal).

**Why it works.**
- Mobile capture is fast (Linear iOS app). The founder logs customer calls from the train.
- Linear MCP gives both Claudes structured read+write.
- Free tier (250 active issues + 2 teams) sustains 6 months at the SDG burn rate.
- Documents-as-first-class-citizens removes the Notion-vs-issue-tracker tension.

**Keep / change.**
- KEEP the structure. Generalize the project names. The seven projects should be **opt-in modules** in the stack:
  - **Core (mandatory):** Strategy, Spec, Sync Queue, Build Log
  - **Optional (commercial projects):** GTM, Customers, Outreach Log
  - Founder picks at bootstrap which modules apply.
- The `project-bootstrap` skill proposes the right module set based on the one-paragraph project description.

## Pattern 3 — GitHub-Canonical Code, Linear-Mirrored Docs

**The pattern.**
- Code, tests, infrastructure → only in GitHub. Never copied to Linear.
- Strategy, specs, decisions, GTM → dual-source. Linear is the live editing surface; `docs/` in the repo is the version-controlled mirror.
- Operational data (prospects, conversation log, outreach) → only in Linear. Never copied to GitHub.
- Research artifacts → KB temporarily during research, migrated to `docs/research/` in repo once stable.

**Why it works.**
- Each tool stays in its zone of competence. Linear is bad at code; git is bad at fast capture.
- The mirror is one-directional at the document level: Linear is the editing surface; the repo mirror is regenerated by Code-Claude.
- Conflict cases (rare) raise a `sync:conflict` Sync Queue issue rather than auto-resolving.

**Keep / change.**
- KEEP. Generalize: "Linear" → "issue-tracker-with-docs" and provide the alternative-tool matrix.

## Pattern 4 — Sync Queue

**The pattern.** A dedicated Linear project where every pending change Chat-Claude makes generates an issue labeled `sync:pending`. Code-Claude, at the start of every terminal session, reads the Sync Queue and propagates the pending changes into the repo before doing anything else. After committing, it changes the label to `sync:synced` and closes the issue.

**Why it works.**
- Founder never copy-pastes between systems.
- Sync state is visible (mobile Linear app shows it).
- If Chat-Claude and Code-Claude make conflicting changes between sessions, the queue catches it.
- It is the simplest possible coordination protocol between two stateless agents.

**Keep / change.**
- KEEP. This is the cleanest single innovation in the SDG architecture. Generalize as a first-class part of the stack.

## Pattern 5 — Strategic vs Build-Time ADR Split (SDG D-019)

**The pattern.** Two ADR classes:
- **Strategic ADRs** (business model, scope, regulatory posture, GTM, pricing, customer commitments): get their own Linear issue in Strategy project, label `type:long-lived`, status `Done`. ALSO mirrored to `docs/decisions/NNNN-*.md` in the repo via Sync Queue.
- **Build-time ADRs** (libraries, encoding, parser conformance, file formats, internal API patterns, test infrastructure): live ONLY at `docs/decisions/NNNN-*.md` in the repo. One-line cross-reference in the parent build issue's session-end comment.
- **Borderline cases** default to strategic.

Numbering is continuous (D-001, D-002, …). Both classes share the sequence.

**Why it works.**
- Build-time ADRs are noisy (one per library choice). Forcing them through Linear creates clutter without adding value for non-engineers.
- Strategic ADRs need a non-engineer-accessible view; Linear documents do that.
- The numbering is shared so search-by-D-number always finds the decision regardless of class.

**Keep / change.**
- KEEP. The split is non-obvious and earned. Document it as a default rule with a clear classification heuristic.

## Pattern 6 — Standing CLAUDE.md at Repo Root

**The pattern.** A `CLAUDE.md` file at the repo root that Code-Claude reads at every session start. Contains:
- Project identity (name, prefix, current phase)
- Source-of-truth rules (which tool owns what)
- Bidirectional sync protocol (steps at session start, steps when making an ADR)
- Architecture decisions that are "locked, do not re-litigate"
- Build conventions (commit message format, test framework, language version)
- "What you're not doing" (out-of-scope discipline list)
- Hard constraints (pinned dependencies, regulatory must-haves)
- Knowledge cutoff caveat (verify versions, don't trust training data on libs)

**Why it works.**
- Code-Claude has stateless context per session. CLAUDE.md is the only thing it carries between sessions automatically.
- The "do not re-litigate" section prevents drift across sessions.
- The "what you're not doing" section is the discipline mechanism.

**Keep / change.**
- KEEP. Template-ize aggressively. The public stack provides a CLAUDE.md skeleton with placeholders. SDG-specific sections (SDG-36 GitHub MCP tool-priority, SDG-37 context-window discipline) become parameterized.

## Pattern 7 — Build Session Discipline

**The pattern.** Every Claude Code build session follows:
1. **Pre-flight checklist** (read Sync Queue, read relevant Linear docs, confirm goal, estimate token budget)
2. **Goal definition** (one sentence, success criteria, out-of-scope)
3. **Eye-test** (look at last session's output if any)
4. **Triage** (any pre-existing issues that need to land first)
5. **Issue filing** (file Linear issues for sub-tasks)
6. **Drafting session prompt** (with as-shipped interfaces from prior session, saved to Linear "session prompts" document before deployment)
7. **Execution** (with `commit-on-green`, `three-strikes-stop`, `4h cap` rules)
8. **Status comments** (per SDG-37 protocol)
9. **`make check`** against the final commit before session handoff
10. **Handoff** (note in Linear what's next, session prompt for next session)

**Why it works.**
- The pre-flight is what prevents wasted sessions.
- The session prompt anchored to as-shipped interfaces is what makes multi-session features tractable.
- `make check` on the final commit catches the "looks done but doesn't pass tests" failure mode.

**Keep / change.**
- KEEP. Extend with explicit TDD gates (red → green → refactor) per `07_session_discipline_design.md`.
- Extend with explicit token-budget pre-flight (estimated tokens per file × files touched, abort if >150k).

## Pattern 8 — Four-Hat Adversarial Review

**The pattern.** After every major specification (new or substantially revised Linear Document in Product or Strategy projects), Chat-Claude proposes a four-hat adversarial review with a one-line confirm gate. Hats:
- Hat 1: **Skeptic / kill-or-go reviewer** — would this kill the project if wrong?
- Hat 2: **Implementation reviewer** — can this be built within the timebox?
- Hat 3: **Customer / external reviewer** — would the target audience accept this?
- Hat 4: **Future-self reviewer** — what does the 6-month-future-founder say about this decision?

Hats output severity × effort × lock-in for each finding. Reviews land as Linear Documents titled `<Spec name> — Adversarial Review v<N>` in the same project as the reviewed spec. Spec docs carry a `Review status:` header field.

Reviews are out-of-scope-fenced against locked strategic decisions and current timeboxes. Findings that would revisit locked decisions become `Open questions for founder`, not findings.

**Why it works.**
- Solo founder has no peer review. The four hats are the cheapest available substitute.
- The structured severity rubric prevents "feels off, can't articulate".
- Out-of-scope fencing prevents adversarial review from becoming an "everything you've ever decided is wrong" exercise.

**Keep / change.**
- KEEP. This is the second-most-defensible innovation (after Sync Queue). Generalize the protocol document; provide the four hats as a default with `<HAT>` placeholders so founder can customize per project.
- Provide hat templates as part of the public stack.

## Pattern 9 — Dual-Model Code Review at PR

**The pattern (SDG D-013).** At PR-ready time, run `scripts/review.py` which sends the diff to two LLMs (one Claude, one OpenAI). Both must score below a `severity:blocker` threshold for the PR to merge. Caveat: D-013 amendment flagged data-residency tension if OpenAI calls cross EU boundaries; resolution per project context.

**Why it works.**
- Catches blind spots of any single model (the canonical worked example: Albumentations 2.0.8 → 2.0.9 silently switched to AGPL, would have torpedoed any commercial deploy; the dual-model catch was the trigger for adopting D-013).

**Keep / change.**
- KEEP, but document as an **opt-in** layer. Solo founders without commercial-scale concerns can ship without it. Document the OpenAI-residency caveat as a known issue.

## Pattern 10 — Calibration-First Evals Pattern

**The pattern.** When introducing any automated evaluation (rubric scorer, eval gate), run 3–5 dense-feedback cycles where the founder eye-tests the same items the evaluator scores. Compute alignment (Spearman or similar). Only after alignment is established does the evaluator get graduated autonomous trust.

**Why it works.**
- Avoids the "evaluator drift" failure mode where automated eval scores stop tracking what the founder actually cares about.
- Cheap insurance: 3–5 cycles is a few hours.

**Keep / change.**
- KEEP. Generalize: applies to any LLM-as-judge or LLM-as-scorer setup. Add as a default protocol in the review-and-QA design doc.

## Pattern 11 — Weekly Build Log

**The pattern.** One Linear issue per ISO week (e.g. `2026-W18`). Body has fixed sections:
- What landed this week
- What did NOT land (carryover)
- Next week plan
- Customer signals this week (optional)
- Mood / energy / risks
- Synced to GitHub (cross-reference to Sync Queue)

Written Friday afternoon (~30 min). Mirrors to `build-log/YYYY-WNN.md` in repo.

**Why it works.**
- Solo founders need a forcing function for honest reflection on velocity, mood, and signal.
- The Friday cadence is a Schelling point — easy to default to.
- Mood / energy is the leading indicator the founder eye-tests every Saturday morning.

**Keep / change.**
- KEEP. Provide as template.

## Pattern 12 — Standing Protocols as Linear Documents

**The pattern.** Repeatable processes live as Linear Documents titled `<Process name> — Standing Protocol`. Examples in SDG: `Adversarial Review Process — Standing Protocol`. Chat-Claude triggers the process by reference ("Run the standing review"), not by re-quoting the steps.

**Why it works.**
- Process knowledge is centralized and editable.
- Chat-Claude's behavior commitment ("propose the standing review when a spec is finalized") can reference the protocol doc by name rather than carrying the steps in the project instructions.

**Keep / change.**
- KEEP. The public stack provides a folder `protocols/` in the recommended Linear structure plus markdown copies in the repo.

## Pattern 13 — Numbered KB Files with `LOAD_FIRST` Discipline

**The pattern.** KB files numbered `00_*` through `09_*`. File `01_LOAD_FIRST_*` is the orientation doc. File `00_PROJECT_INSTRUCTIONS.md` is the Settings paste. Numbering imposes load order.

**Why it works.**
- New chats are easier to bootstrap: "search 01_LOAD_FIRST first" is the universal opener.
- Drift is visible: when files are out of date, the date-stamped header makes it obvious.

**Keep / change.**
- KEEP for the meta-project's KB (which is what this very file is part of).
- For the public stack, recommend it as a pattern but acknowledge the alternative: per-topic markdown files indexed in README. Either works; pick one and commit.

## Pattern 14 — Hard Founder Constraint: No Manual Updates

**The pattern.** The founder commits to never manually copying content between Linear and GitHub. Chat-Claude writes Linear. Code-Claude writes GitHub. The Sync Queue moves things between them.

**Why it works.**
- Removes the most common failure mode of multi-tool systems (drift between sources).
- Forces the architecture to actually work; the moment manual copy-paste creeps in, the design is broken.

**Keep / change.**
- KEEP. State explicitly in the public stack README as the discipline this design assumes.
